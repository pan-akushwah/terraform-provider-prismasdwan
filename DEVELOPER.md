Developer Guide
===============

This guide covers building the Prisma SD-WAN Terraform provider from source,
running a local build with Terraform, and debugging and troubleshooting
provider behavior.

For resource and data source reference, see the
[Terraform Registry documentation](https://registry.terraform.io/providers/PaloAltoNetworks/prismasdwan/latest/docs).

Repository layout
-----------------

| Path                                  | Contents                                                                |
|---------------------------------------|-------------------------------------------------------------------------|
| `main.go`                             | Provider entry point. Also holds the `go generate` directives for docs. |
| `internal/provider/`                  | Provider, resources (`*_rs.go`) and data sources (`*_ds.go`).           |
| `sdk/`                                | API client: authentication, HTTP transport, logging and retries.        |
| `sdk/sdwan/schemas/`                  | Go structs for API request and response bodies.                         |
| `sdk/sdwan/services/`                 | Executes an API request for a resource.                                 |
| `docs/`                               | Registry documentation, generated by `tfplugindocs`.                    |
| `templates/`                          | Templates used by `tfplugindocs`.                                       |
| `examples/provider/`                  | Provider configuration example.                                         |
| `examples/resources/<name>/`          | `resource.tf` and `import.sh` for each resource.                        |
| `examples/data-sources/<name>/`       | Example for each data source.                                           |
| `examples/automated_examples/<name>/` | Complete, runnable configurations with variables and outputs.           |

> **Generated code:** most files under `internal/provider/`, `sdk/sdwan/` and
> `docs/` are generated. Files that start with a "This code is automatically
> generated" header are overwritten when the provider is regenerated. If you
> find a bug in one of them, open an issue with the details rather than relying
> on a local edit.


Building the provider
---------------------

### Requirements

- [Go](https://go.dev/dl) 1.22 or later
- [Terraform](https://developer.hashicorp.com/terraform/install) 1.0 or later

### Build

```sh
git clone https://github.com/PaloAltoNetworks/terraform-provider-prismasdwan
cd terraform-provider-prismasdwan
make build
```

`make build` formats all Go code with `gofmt -s -w .` and then runs
`go build`. The provider binary, `terraform-provider-prismasdwan`, is written
to the repository root.

### Make targets

Run `make` or `make help` to list the targets.

| Target         | Description                                                                                                           |
|----------------|-----------------------------------------------------------------------------------------------------------------------|
| `make build`   | Format the code and build the provider binary.                                                                        |
| `make test`    | Run unit tests (`go test ./...`).                                                                                     |
| `make verbose` | Run unit tests with verbose output.                                                                                   |
| `make bench`   | Run benchmarks.                                                                                                       |
| `make clean`   | **Deletes all generated resources, data sources, docs and examples.** Only use this before regenerating the provider. |

### Regenerating documentation

```sh
go generate ./...
```

This runs `terraform fmt -recursive ./examples/` and then `tfplugindocs`,
which rebuilds `docs/` from the provider schema, `templates/` and `examples/`.


Using a local build with Terraform
----------------------------------

Terraform's
[development overrides](https://developer.hashicorp.com/terraform/cli/config/config-file#development-overrides-for-provider-developers)
make it use your local binary instead of downloading the provider from the
registry.

1. Create or edit the Terraform CLI configuration file: `~/.terraformrc` on
   Linux and macOS, or `%APPDATA%\terraform.rc` on Windows.

   ```hcl
   provider_installation {
     dev_overrides {
       "paloaltonetworks/prismasdwan" = "/path/to/terraform-provider-prismasdwan"
     }

     direct {}
   }
   ```

   The value is the directory that contains the built binary, which is the
   repository root after `make build`.

2. Use the same source address in your configuration:

   ```hcl
   terraform {
     required_providers {
       prismasdwan = {
         source = "paloaltonetworks/prismasdwan"
       }
     }
   }
   ```

3. Run `terraform plan` or `terraform apply` directly. You don't need
   `terraform init` for an overridden provider. Terraform prints a warning
   that development overrides are in effect; that's expected.

After every code change, run `make build` again. Terraform picks up the new
binary on the next command.

> Remove or comment out the `dev_overrides` block when you're done, otherwise
> every configuration on your machine keeps using the local build.


Provider configuration
----------------------

Each setting can come from the provider block, an environment variable, or a
JSON file given by `auth_file`. When a setting is defined in more than one
place, the order of precedence is:

1. The provider block
2. Environment variables
3. The `auth_file` JSON file

| Provider attribute | Environment variable          | JSON key                  | Default                                                              |
|--------------------|-------------------------------|---------------------------|----------------------------------------------------------------------|
| `client_id`        | `SCM_CLIENT_ID`               | `client_id`               | *(required)*                                                         |
| `client_secret`    | `SCM_CLIENT_SECRET`           | `client_secret`           | *(required)*                                                         |
| `scope`            | `SCM_SCOPE`                   | `scope`                   | *(required)*, for example `tsg_id:1234567890`                        |
| `host`             | `SCM_HOST`                    | `host`                    | `api.sase.paloaltonetworks.com`                                      |
| `auth_url`         | `SCM_AUTH_URL`                | `auth_url`                | `https://auth.apps.paloaltonetworks.com/auth/v1/oauth2/access_token` |
| `protocol`         | `SCM_PROTOCOL`                | `protocol`                | `https`                                                              |
| `port`             | `SCM_PORT`                    | `port`                    | Standard port for the protocol                                       |
| `headers`          | `SCM_HEADERS` (JSON object)   | `headers`                 | None                                                                 |
| `timeout`          | `SCM_CLIENT_TIMEOUT`          | `timeout`                 | `60` (seconds)                                                       |
| `logging`          | `SCM_LOGGING`                 | `logging`                 | `quiet`                                                              |
| `auth_file`        | –                             | –                         | None                                                                 |
| –                  | `SCM_SKIP_VERIFY_CERTIFICATE` | `skip_verify_certificate` | `false`                                                              |

Certificate verification can't be disabled from the provider block. This is
intentional, so that the setting can't be committed in a configuration by
mistake. Use the environment variable only while troubleshooting.

### Example: credentials from the environment

Keep secrets out of `.tf` files by using environment variables:

```sh
export SCM_CLIENT_ID="terraform@1234567890.iam.panserviceaccount.com"
export SCM_CLIENT_SECRET="<client-secret>"
export SCM_SCOPE="tsg_id:1234567890"
```

```hcl
provider "prismasdwan" {}
```

### Example: credentials from a JSON file

```json
{
  "client_id": "terraform@1234567890.iam.panserviceaccount.com",
  "client_secret": "<client-secret>",
  "scope": "tsg_id:1234567890",
  "logging": "basic"
}
```

```hcl
provider "prismasdwan" {
  auth_file = "~/.config/prismasdwan/auth.json"
}
```

### Example: custom headers

```sh
export SCM_HEADERS='{"X-Request-Source": "ci-pipeline"}'
```

### Proxies

The provider honors the standard `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`
environment variables.


Debugging
---------

The provider has three debugging tools. Use them in this order:

1. **Provider logging**, to see which API calls are made.
2. **Request dump files**, to see the full request and response for each call.
3. **A debugger** such as Delve, to step through provider code.

### 1. Provider logging

Provider logs are written at the Terraform `DEBUG` level, so you must enable
Terraform logging **and** set the provider logging level.

| `logging` value | What is logged                                                   |
|-----------------|------------------------------------------------------------------|
| `quiet`         | Nothing (default).                                               |
| `basic`         | The method and URL of each API call, and access token refreshes. |
| `detailed`      | Full HTTP requests and responses, including headers and bodies.  |

```sh
export TF_LOG_PROVIDER=DEBUG          # provider logs only; use TF_LOG=DEBUG for Terraform core too
export TF_LOG_PATH=./terraform-debug.log
export SCM_LOGGING=basic              # or "detailed"

terraform apply
```

Example `basic` output:

```text
[DEBUG] provider.terraform-provider-prismasdwan: [GET] https://api.sase.paloaltonetworks.com/sdwan/v2.1/api/profile
[DEBUG] provider.terraform-provider-prismasdwan: [POST] https://api.sase.paloaltonetworks.com/sdwan/v2.0/api/globalprefixfilters
```

Notes:

- A `GET /sdwan/v2.1/api/profile` call before each SD-WAN API call is
  expected.
- In `detailed` mode, each request and response can appear twice in the log.

> **Security warning:** any level other than `quiet` writes the API access
> token (JWT) to the log. `detailed` also writes the `Authorization` header and
> full request bodies. Treat these logs as secrets: don't commit them, and
> redact them before sharing. Access tokens expire, but they're valid until
> then.

### 2. Request dump files

Set `SDWAN_DUMP_PATH_DIR` to an existing directory, and the provider writes
one JSON file for every SD-WAN API request it makes:

```sh
mkdir -p /tmp/sdwan-dump
export SDWAN_DUMP_PATH_DIR=/tmp/sdwan-dump

terraform apply
```

Files are named `<unix-time-ms>.<resource-type>.<METHOD>.<uuid>.json`. Sorting
by name gives the order of the calls:

```text
1767225600123.prismasdwan_global_prefix_filter.POST.4b1c...json
1767225600456.prismasdwan_global_prefix_filter.GET.9e2f...json
```

Each file contains:

| Field                | Description                                                                          |
|----------------------|--------------------------------------------------------------------------------------|
| `ResourceType`       | Terraform resource type that made the call.                                          |
| `Method`             | HTTP method.                                                                         |
| `Path`               | API path template, for example `/sdwan/v2.1/api/elements/{element_id}/ntp/{ntp_id}`. |
| `PathParameters`     | Values substituted into the path.                                                    |
| `FinalPath`          | Path after substitution.                                                             |
| `RequestBody`        | JSON body that was sent.                                                             |
| `ResponseStatusCode` | HTTP status code.                                                                    |
| `ResponseBytes`      | Response body, **base64-encoded**.                                                   |

Decode a response body with `jq`:

```sh
jq -r '.ResponseBytes | @base64d' /tmp/sdwan-dump/<file>.json | jq .
```

List every failed call:

```sh
for f in /tmp/sdwan-dump/*.json; do
  jq -r 'select(.ResponseStatusCode >= 400)
         | "\(.ResponseStatusCode) \(.Method) \(.FinalPath)"' "$f"
done
```

Dump files don't contain credentials or access tokens, but request and
response bodies can contain configuration values such as pre-shared keys or
passwords. Review them before sharing.

### 3. Running under a debugger

The provider supports Terraform's debug mode, which lets you attach a
debugger such as [Delve](https://github.com/go-delve/delve).

1. Build without optimizations:

   ```sh
   go build -gcflags="all=-N -l" -o terraform-provider-prismasdwan
   ```

2. Start the provider in debug mode:

   ```sh
   dlv exec --accept-multiclient --continue --headless --listen=:2345 \
     ./terraform-provider-prismasdwan -- -debug
   ```

   Or, without a debugger, run `./terraform-provider-prismasdwan -debug`.

3. The provider prints a `TF_REATTACH_PROVIDERS` value. Export it in the
   shell where you run Terraform:

   ```sh
   export TF_REATTACH_PROVIDERS='{"registry.terraform.io/paloaltonetworks/prismasdwan":{...}}'
   terraform plan
   ```

4. Connect your IDE's debugger to `localhost:2345` and set breakpoints. Useful
   places to start:
    - `Create`, `Read`, `Update` and `Delete` in
      `internal/provider/<resource>_rs.go`
    - `ExecuteSdwanRequest` in `sdk/sdwan/services/sdwan_client.go`, which
      handles every API call
    - `Do` in `sdk/client.go`, which handles HTTP, retries and token refresh

The configuration's `required_providers` source must be
`paloaltonetworks/prismasdwan` for Terraform to use the reattached provider.

Troubleshooting
---------------

### How API errors appear

API errors are shown in Terraform diagnostics as:

```text
[HTTP <status>] <error-code> <message> - <details>
```

For example:

```text
[HTTP 400] REQUEST_VALIDATION_FAILED Invalid value for field 'name' - ...
```

Search for the error code in the logs or dump files to find the exact request
that failed.

### Automatic retries

The provider retries some failures before reporting an error:

| Response                          | Behavior                                                                             |
|-----------------------------------|--------------------------------------------------------------------------------------|
| `401 Unauthorized`                | Refreshes the access token and retries once. A second `401` is reported as an error. |
| `429`, `500`, `502`, `503`, `504` | Retries up to 5 times with a short delay between attempts.                           |
| `404 Not Found`                   | Not retried. During refresh, the resource is removed from state.                     |
| Any other error                   | Not retried.                                                                         |

### Common problems

#### `Provider parameter value error: ClientId must be specified`

The same pattern applies to `ClientSecret` and `Scope`. The value isn't set in
the provider block, the environment, or the `auth_file`. Check:

```sh
env | grep '^SCM_'
```

Environment variables must be exported in the same shell that runs
Terraform.

#### `AuthUrl should start with http:// or https://`

`auth_url` or `SCM_AUTH_URL` is set to a value without a scheme. Remove it to
use the default.

#### Authentication fails with `401`

- `scope` must be in the form `tsg_id:<tenant-service-group-id>`.
- Check that the service account belongs to that tenant service group and has
  a role that permits SD-WAN configuration.
- Check that the client secret hasn't been rotated or expired.
- Run with `SCM_LOGGING=basic` and `TF_LOG_PROVIDER=DEBUG` to confirm that a
  token refresh happens and which host is called.

#### `unknown host: cannot determine URI`

`host` is set to a value the provider doesn't recognise. Use the default
(`api.sase.paloaltonetworks.com`) unless you've been given a different API
host for your tenant.

#### TLS or certificate errors behind an inspecting proxy

Add the proxy's CA certificate to the system trust store. As a temporary
diagnostic only, you can disable certificate checks:

```sh
export SCM_SKIP_VERIFY_CERTIFICATE=true
```

Don't use this setting in production.

#### Errors when many resources change at once

Some SD-WAN APIs use version-based (`_etag`) optimistic locking and reject
concurrent changes to the same collection. The provider sends requests for
these resource types one at a time. If you still see conflict or version
errors:

- Make sure nothing else changes the same objects at the same time, such as
  another Terraform run, a script, or the management UI.
- Re-run the failed command. Terraform only retries resources that didn't
  finish.
- As a last resort for a single run, lower Terraform's parallelism:

  ```sh
  terraform apply -parallelism=1
  ```

Use a dump directory to find the call that failed. Its status code and
response body show which object conflicted.

#### A resource keeps being recreated, or disappears from state

If a read returns `404`, the provider assumes the object was deleted outside
Terraform and removes it from state. The next plan then proposes to create it
again. Check whether the object still exists in the management UI, and
whether its parent (site, element, policy set) was deleted or replaced.

#### A plan shows changes after every apply

This means the value the API returns differs from the configured value. For
example, the API normalises a value, reorders a list, or adds defaults.

1. Run `terraform plan` and note the attribute that changes.
2. Run `terraform apply` with `SDWAN_DUMP_PATH_DIR` set.
3. Compare `RequestBody` in the `PUT` or `POST` dump file with the decoded
   `ResponseBytes` of the `GET` that follows it.

Where the API normalises the value, match the API's form in your
configuration. Otherwise, report it as an issue with both bodies.

#### Importing existing objects

Resources are imported by their Terraform ID (`tfid`).

- **Top-level resources** use the object ID:

  ```sh
  terraform import prismasdwan_global_prefix_filter.example "<filter-id>"
  ```

- **Nested resources** use the object ID followed by the parent path
  parameters, separated by `:`:

  ```text
  <object-id>:<param>=<value>:<param>=<value>
  ```

  ```sh
  terraform import prismasdwan_element_interface.wan1 \
    "<interface-id>:site_id=<site-id>:element_id=<element-id>"
  ```

  The parameter names match the placeholders in the resource's API path. To
  find them, check the resource's documentation, or create a similar resource
  with a dump directory set and look at `PathParameters`.

The `tfid` of a resource already in state shows the exact format:

```sh
terraform state show prismasdwan_element_interface.wan1 | grep tfid
```

Reporting an issue
------------------

Open an issue on
[GitHub](https://github.com/PaloAltoNetworks/terraform-provider-prismasdwan/issues)
and include:

- Provider version (`terraform version` shows it) and Terraform version
- The smallest configuration that reproduces the problem
- The full error message
- The dump files for the failing operation, or a `basic` log

**Before attaching anything, remove** client IDs and secrets, access tokens
and `Authorization` headers, tenant IDs if you consider them sensitive, and
any secret values in request bodies.
